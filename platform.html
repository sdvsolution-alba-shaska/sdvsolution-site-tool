SDVsolution / Platform

One model for requirements, architecture and every ECU.

The platform holds the vehicle as a single connected model. Requirements, signals, connector pins, ECUs and tests are all in it, so the tool can check them against each other instead of leaving that to a review meeting.

Requirements across the V

System, software and hardware requirements sit in one model with the architecture, the detailed design and the state machines they lead to.

  • A guided template for the requirement sentence, so each one has a trigger, a condition and a response
  • A live check on every requirement: one statement, verifiable, unambiguous
  • Trace in both directions, from stakeholder need to the test that proves it
  • Impact view: click a requirement or a signal and see everything a change would touch

Reviews, baselines and readiness

Approvals and configuration management are part of the model, not a separate process on paper.

  • Joint review with comments, decisions and approvals recorded
  • Versioned baselines with a diff between any two, and restore
  • A readiness dashboard across safety, cybersecurity, review status and the quality check
  • Release tracking: deliverables, evidence and sign-off for every ECU

Vehicle architecture and communication

The topology, the communication matrix and the wiring are imported and then compared with each other.

  • Buses, frames and signals from DBC, LDF and ARXML
  • Wiring drawings read from PDF: every wire traced from pin to pin
  • I/O list against drawing: wrong pins, outputs with no wire, wired pins missing from the list
  • Bus membership against the drawings: nodes that have signals but no wiring, and the reverse

A specification for every ECU

Each ECU gets its own requirement specification, generated from the buses it is on, the connectors it has and the safety level it carries.

  • Hardware constraints, software, diagnostics, update, cybersecurity and verification
  • Connector pin-outs and an I/O list per ECU
  • Features deployed to the ECUs that host them, including features that span several ECUs
  • Ready to hand to the ECU supplier

The assistant reads what you already have

Drop a file into the assistant and ask in plain language. It answers from your live model and drafts requirements and updates for your engineers to review. It supports your team; it does not replace engineering judgment.

FileWhat the platform does with it
PDF, WordReads specifications and standards, and drafts requirements from them
ExcelImports requirement lists, I/O lists and release plans
DBC, LDFImports CAN and LIN buses with their frames and signals
ARXMLImports the system description: clusters, ECUs, signals and software components
Wiring drawings (PDF)Traces every net and builds the pin-to-pin connection list

Where it sits in Automotive SPICE

The platform is organised around the process areas an assessor will ask about.

Process areaIn the platform
System engineeringSystem requirements, system architecture, integration and qualification test (SYS.2 to SYS.5)
Software engineeringSoftware requirements, architecture, detailed design and unit construction, with unit, integration and qualification test (SWE.1 to SWE.6)
Hardware engineeringHardware requirements, design and verification (HWE.1 to HWE.4)
Supporting processesJoint review, configuration management and change request management (SUP.4, SUP.8, SUP.10)
Safety and cybersecuritySafety level and cybersecurity attributes on each requirement, in line with ISO 26262 and ISO/SAE 21434
