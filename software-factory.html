SDVsolution / Software factory

Code for each feature. Software for each ECU. One package for the vehicle.

A behavior model describes what a feature does. The software factory turns each approved model into C code and unit tests, then integrates the features deployed on an ECU into the software for that ECU.

How a feature becomes software

Model the behavior

States, transitions, inputs, outputs, timing and calibration values. An agent can propose the model from the feature's requirements; an engineer approves it.

Generate the feature

C source and header for the feature, with unit tests that drive it through its scenarios and check outputs, states and timing.

Integrate the ECU

Every feature deployed on the ECU is wired together: signals routed between features, a schedule, and an integration test for the whole ECU.

Assemble the vehicle

One package with every ECU, plus a list of the signals that cross between ECUs so the buses can be checked.

The target ECU comes from the deployment

You decide once where each feature runs. A window feature runs on the door modules, a seat feature on the seat modules, climate on the front zone. The factory reads that deployment and builds each ECU from the features it hosts.

  • A feature can run on several ECUs, such as all four door modules
  • Two features that write the same signal are caught before code is generated
  • Calibration values stay separate per feature

What is in an ECU package

A folder you can build. The makefile compiles the package and runs the integration test.

  • One software component per feature, with its own unit test
  • The integration layer: ECU header, signal routing and task schedule
  • An integration test that replays each feature's scenarios through the ECU's inputs
  • An AUTOSAR composition description (ARXML) and a manifest of what was built

How it is checked

Generated code is only useful if you can trust it, so the factory tests what it writes.

Compiled with strict warnings

Generated packages are compiled with the compiler's warnings turned on and treated as errors.

Tested at two levels

Each feature has unit tests. Each ECU has an integration test that runs every feature's scenarios again once the features are wired together.

The tests are tested

We plant deliberate faults in the integration layer and check that the integration test catches them.

Your engineers stay in charge

Models are proposed, then reviewed and approved by an engineer. Only approved models go into a release package.
